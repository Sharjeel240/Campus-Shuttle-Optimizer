## 1. Project Title

**Campus Shuttle Optimizer: An Intelligent Routing and Capacity Scheduling System Using Graphs, Greedy Algorithms, and Dynamic Programming**

## 2. Project Objective

Develop a working campus transportation simulator that optimizes shuttle routes, allocates limited passenger capacity, schedules trips, and evaluates system performance under unexpected travel delays.

The project must demonstrate practical implementations of graph algorithms, greedy algorithms, dynamic programming, complexity analysis, and optimization experiments.

This is an academic project for DAA Review 2, which evaluates system design, implementation progress, prototype demonstration, correctness, and performance.

## 4. Real-World Problem

A university campus has multiple shuttle stops connected by roads with different travel times. Several shuttles operate with limited seating capacity and shift schedules. Students submit transportation requests, and traffic disruptions can increase journey times.

The application must determine:

1. Efficient network connections between important stops.
2. Shortest routes between stops.
3. Which passenger requests should be prioritized when capacity is limited.
4. Which shuttle trips can be scheduled without conflicts.
5. How to construct practical multi-stop shuttle routes.
6. How to respond to random delays and road disruptions.
7. Whether the proposed optimization improves transportation performance.

Use realistic synthetic data rather than inventing claims about real campus performance.

## 5. Core Modules and Algorithms

### Module A: Campus Network Modeling

Represent the campus as a weighted graph.

- Vertices represent shuttle stops.
- Edges represent roads between stops.
- Edge weights represent travel time in minutes.
- Support directed or undirected edges as appropriate.
- Store the graph using adjacency lists.
- Include configurable stops, depots, connections, and travel times.
- Provide a visual network map with labeled stops and weighted connections.

Provide a sample campus dataset with at least 10–15 stops, multiple depots, and enough connections to test different graph structures.

Allow users to add, edit, and remove stops and road connections through the dashboard.

### Module B: Minimum Spanning Tree

Implement both:

1. Prim's algorithm.
2. Kruskal's algorithm.

Requirements:

- Use a priority queue for Prim's algorithm and a disjoint-set union structure for Kruskal's algorithm.
- Display the resulting minimum spanning tree.
- Show total network connection cost or travel-time weight.
- Compare both algorithms' execution times.
- Explain why an MST is useful for connecting critical stops.

Important: Clearly state that an MST provides a low-cost network backbone, not necessarily the optimal passenger-serving shuttle route.

### Module C: Single-Source Shortest Paths

Implement:

1. Dijkstra's algorithm using an adjacency list and binary heap.
2. Bellman–Ford algorithm for graphs that may contain negative edge weights.

Requirements:

- Let users select source and destination stops.
- Show the shortest path, total travel time, and route sequence.
- Highlight the selected route on the network visualization.
- Display the algorithm's execution time.
- Reject negative weights when running Dijkstra.
- Detect reachable negative-weight cycles using Bellman–Ford.
- Do not use negative travel times in the normal campus scenario.

Explain the correctness assumptions and time complexity of each algorithm.

### Module D: All-Pairs Shortest Paths

Implement Floyd–Warshall manually.

Requirements:

- Compute shortest travel times between every pair of stops.
- Display a shortest-distance matrix.
- Allow users to select any source-destination pair.
- Reconstruct and display the corresponding shortest path.
- Handle unreachable nodes correctly.
- Compare its execution time with Dijkstra on appropriate test graphs.
- Explain when Floyd–Warshall is appropriate and its O(V³) time complexity.

### Module E: Passenger Prioritization Using 0/1 Knapsack

Each passenger group or transport request must have:

- Request ID
- Pickup stop
- Destination stop
- Number of passengers
- Priority or service value
- Optional deadline
- Estimated journey time

Implement 0/1 Knapsack using dynamic programming.

Requirements:

- The user sets shuttle capacity.
- Select requests that maximize total service value without exceeding capacity.
- Each request is either selected completely or rejected; do not partially select a passenger group.
- Display selected requests and rejected requests.
- Show total passengers served, remaining seats, total service value, and utilization percentage.
- Include a DP table or clear step-by-step explanation for a small example.
- Validate that capacity is not exceeded.

Explain why the algorithm has O(nC) time complexity, where n is the number of requests and C is capacity.

Treat the service value as a configurable priority score, not as a guaranteed real-world measure of passenger satisfaction.

### Module F: Greedy Scheduling

Implement:

1. Activity selection based on earliest finishing time.
2. Job sequencing with deadlines and service rewards.

Requirements:

- Generate or import shuttle trip requests with start times, finish times, deadlines, and priorities.
- Select compatible activities for a single shuttle.
- Implement job sequencing with deadlines using a suitable greedy strategy.
- Display scheduled and rejected trips.
- Show a visual timetable.
- Explain the assumptions and limitations of each greedy strategy.

Do not claim that activity selection alone solves the full multi-vehicle scheduling problem.

### Module G: Multi-Vehicle Routing

Implement a practical Clarke–Wright savings heuristic for constructing shuttle routes from one or more depots.

Requirements:

- Start from simple depot-to-request routes.
- Calculate route savings for joining compatible requests.
- Merge routes while respecting vehicle capacity and route feasibility.
- Support multiple vehicles.
- Calculate route distance or travel time.
- Show stop sequences and assigned passenger requests for each vehicle.
- Prevent duplicate service of requests.
- Validate capacity, route connectivity, and depot return constraints.
- Display a separate route map for each vehicle or distinguish vehicles by color.
- Explain that this is a heuristic and does not guarantee the globally optimal solution.

Use the shortest-path travel-time matrix where appropriate.

If a route violates capacity or other constraints, reject that merge and preserve a valid solution.

### Module H: Delay and Robustness Simulation

Implement a configurable simulation of uncertain traffic conditions.

Requirements:

- Allow users to set the percentage increase in travel time.
- Simulate random road delays using a configurable random seed.
- Allow users to disable selected road connections to simulate disruptions.
- Recalculate shortest paths after delays or disruptions.
- Re-evaluate feasible routes and passenger allocations when necessary.
- Compare baseline and disrupted scenarios.

Display:

- Average journey time.
- Percentage of requests served.
- Total passengers served.
- Average delay.
- Vehicle capacity utilization.
- Unserved requests.
- Percentage of disrupted road connections.
- Runtime before and after disruption.

Clearly distinguish simulated outcomes from real-world observations.

### Module I: Experimentation and Benchmarking

Provide a dedicated experimentation page.

Test different graph sizes, graph densities, fleet sizes, vehicle capacities, demand volumes, and disruption levels.

Benchmark:

- Prim versus Kruskal.
- Dijkstra versus Bellman–Ford on suitable non-negative graphs.
- Dijkstra repeated from multiple sources versus Floyd–Warshall.
- Greedy scheduling outcomes.
- Knapsack runtime as request count and capacity change.
- Multi-vehicle routing performance under different constraints.

Requirements:

- Use Python's time.perf_counter for runtime measurements.
- Run repeated trials where practical and report average runtimes.
- Record graph size, number of edges, algorithm, runtime, and relevant solution-quality metrics.
- Plot runtime against graph size.
- Plot demand served against capacity.
- Plot journey time against disruption level.
- Export experiment results to CSV.

Use correctness checks to compare solutions where feasible. Explain that measured runtime depends on hardware, input size, implementation, and environment. Do not fabricate benchmark results.
